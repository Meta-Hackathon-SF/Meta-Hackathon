# Can Muse form constellations for 10k–100k players? (2026-11-13)

Author: Adam (`@adamzhang06`). These are three paid experiments on synthetic communities. They used 1k and 5k players, 40 planted meaning archetypes, planted confusable pairs, one giant archetype (26%), noise players, a planted week-2 drift and optional activity.
- **Truth:** used only for scoring.
- **Pipeline:** every Muse call went through the production `MuseAdapter` and the capped evalkit ledger, which records counts only.
- **Spend:** $5.11 in total (X-A $2.10, X-C $1.71, X-D $1.30).
- **Code:** the scratch experiment code is not in the repo. This document records the results and the design they support.

Treat every number as directional:
- each 5k configuration ran once;
- the 1k F1 varied .38–.66 across 5 reruns of the same configuration;
- the data is synthetic.

## Answer

**Yes, but not as one call, and not as one call per shard either.**

The measured design has three stages:
1. **Muse reads** every answer once, as it arrives, against a small taxonomy that Muse writes.
2. **Code partitions** the community into meaning blocks of at most about 100 players.
3. **Muse forms the 3–5 person constellations inside each block** with the existing M4 call. M4 works well at that size.

Projected cost is about **$2 a week at 10k players and $15–20 at 100k**. Most of the work runs during the week, so Sunday's critical path is a few minutes.

## Findings

### 1. One M4 call breaks at about 200 players, long before the token limit

| Players in one call (Ember) | Result |
|---|---|
| ≤100 | 0–6% of ids dropped; purity .38–.53 |
| 200 | Bimodal: one of four runs degenerate |
| 400 | Up to 30% of ids dropped; size violations |
| 800 | **Valid-looking JSON at chance level.** Every group was a consecutive run of input ids. |
| ~1,950 | The 200K-token price cliff, which is irrelevant because quality fails roughly ten times earlier |

- The production adapter's 256 KB payload cap (about 600 players) and today's `MAX_ANSWERS=400` (about 87 players) are therefore the right side of the cliff.
- **Code must reject "groups of consecutive input ids"**: that output passes schema validation and size checks.

### 2. Comparing the three designs

Every design scores well above chance (constellation purity chance is .11; pairwise precision chance is about .03).

| Design | Best accuracy | $/week at 100k | Notes |
|---|---|---|---|
| **A.** Spark taxonomy → Ember labels per answer → Leiden graph clustering | Seed-disjoint group precision .18, true match 35% | ~$22 | Labels were good (Cohen's kappa .80 on relabel). **Leiden on label features was the weak part.** Resolution and k changes made no difference. |
| **C.** Ember groups 100–250-player shards → Spark merges → Ember reconciles | Global-meaning F1 .64 / seed-disjoint .60 at 1k; .56 / .53 at 5k | $4–6 | Cheapest. The giant archetype absorbs its neighbours. Shards of 250 or more sometimes **collapse**: one cluster with 70% of ids silently dropped. From 10k players up, the merge must be a tree. |
| **D.** Ember labels per answer → **code mixture model** | F1 .64 / seed-disjoint .60 on answers alone. **.75–.80 with capped activity signals.** | ~$15 (~$8 with an embedding pre-filter) | The mixture model doubled plain argmax (.33 → .64), so A's ceiling was its clustering, not its labels. Incremental weekly updates keep groups stable. |

- **Same labels, different clustering:** A and D used the same kind of Ember labels. D's code mixture model scored about 3x higher than A's graph clustering. The labelling approach is sound.
- **Wonder and Spark don't help these roles:**
  - **Taxonomy:** a Wonder taxonomy scored no better than Spark (NMI .41 vs .42).
  - **Labelling:** Spark labels cost 16x more and gained +.02.
  - **C's map step:** Spark was 10x the cost and scored lower than Ember (.62 vs .66).
- **Local embeddings** (MiniLM) group by topic, not stance. F1 was .23. Use them only as a cheap "who changed" filter.

### 3. Signals and weights (D, measured)

Meaning comes from answers; behaviour can only break near-ties.

| Signal | Weight | Effect |
|---|---|---|
| Answer meaning | 1 per answer | Essential. Behaviour alone gives F1 .40–.49. |
| Post topics | ≤1 | +.11 F1 at weight 1. At weight 8, harmful overrides outnumber helpful ones. |
| Shared Groups/Events | ≤1 | Same as post topics |
| Activity meaning | ≤2, halved per week of age | Best single boost (.80). Stale activity pins drifters unless capped. |
| Last week's cluster | ≤0.5 | Stability. Weight 2 or more hurts. |
| **All behaviour combined** | **capped at 2 nats per player** | Restores drifter accuracy and keeps group topic diversity (about 11% loss instead of 15%) |

- **Cold start:** players with no activity score the same as those with it (F1 .64), so opting out of activity costs a player nothing.

### 4. Week-to-week

- **Incremental costs the same as a full rerun.** Every player's roughly 4.6 new answers must be labelled to learn who changed. Its advantages are stability and slightly better accuracy (.58 vs .57 F1; only 12% of non-movers regrouped at τ=4).
- **Mover detection** ("fits another cluster by τ nats"): precision/recall .35/.49 at τ=4. Five answers a week is weak evidence. Re-check movers rather than trusting them.
- **New meanings:** the "other" rate is a weak novelty trigger (2–3%). Re-discovering on the low-confidence pool weekly still finds 10–15 new labels.

## Recommended design (not implemented)

1. **Monday:** Spark proposes 25–60 meaning labels from a 150-player sample. This costs about $0.03–0.30.
   - The taxonomy goes in the payload as data, never as instructions.
   - OutputGuard checks every label. It flagged 1 of 199 for a sensitive term.
2. **Daily, as answers arrive:** Ember labels answers in batches of 50 with short codes and random refs: primary label, optional secondary, and intensity.
   - Code validates that every ref appears exactly once and that no codes are invented.
3. **Saturday lock:** a code mixture model combines meaning with capped behaviour (section 3). It partitions players into meaning blocks of at most 100, splitting the giant archetype by a second label.
4. **Sunday precompute:** existing M4 per block, then M5 names per constellation, with the existing validators. Add three checks:
   - reject consecutive-run groupings;
   - re-split any shard that drops more than 30% of ids;
   - forced placement as a last resort, so every player gets exactly one group.
5. **Weekly:** re-discover labels on the low-confidence pool; history weight 0.5.

**Capacity** at 100k players: about 10k Ember calls for labelling, plus about 1k M4 calls.
- **Throughput:** at 20 concurrent calls, labelling takes about 45 min, spread across the week.
- **Token floor:** Sunday is bounded by 4M tokens per minute, which is about 4 min.
- **Scaling limit:** dense similarity needs top-k or approximate nearest neighbours above about 20k players.
- **Cache:** hits were under 5% of tokens, so don't plan on caching.

## Caveats

- In C, the shared meaning rule's examples paraphrase 2 of the 38 planted confusable pairs. This may flatter C's confusable separation.
- Metrics differ between experiments: A reports group precision, C global-meaning F1, D mixture-cluster F1. The table compares each design's best reported number, not one common score.
- No real participant data was used. Accuracy on real answers is unknown until a consented pilot.
